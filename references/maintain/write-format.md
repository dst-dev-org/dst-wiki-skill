# DST Wiki 页面格式

仅新建页、调整元数据／标签／命名／页面结构，或检查这些格式时读取。字段形状、取值、页面布局与标签在本文件维护；索引页格式与组织见 [索引维护](maintain-index.md)。已有案例或陷阱增修沿用原页，无需默认加载本文件。

## 元数据

DST 知识页使用 YAML frontmatter：

```yaml
---
title: 页面标题
created: YYYY-MM-DD
updated: YYYY-MM-DD
type: component | prefab | stategraph | api | mechanism | cookbook
summary: 一句话说明解决的需求
aliases: [必要的需求措辞或标识符]
tags: [来自标签分类法]
dst_build: "实际核验的版本与编号体系"
sources: [components/example.lua]
reliability: verified
validation: source-reviewed | runtime-tested
status: active | review-needed | archived
---
```

`sources` 只列实际核验文件。Frontmatter 作页面级摘要，正文“验证记录”（cookbook 在“边界与验证”内）对应实际审阅／运行覆盖，并注明未覆盖范围。状态与验证语义见知识维护的“证据与状态”；不在正文重复一份页面状态。

项目设计决策归 `docs/decisions/`，不使用游戏知识页格式，也不进入默认知识候选。

可选工具箱 `dst-toolbox` 的 `validate_page.py` 会检查以下字段约束（[校验选择与调用](verify-wiki.md#按变更选择)）；脚本或运行环境不可用时，人工核对同一套规则：

- 非索引页的上述 12 个字段均必填，`type` 须与[页面目录归属](#命名与归属)一致；索引页的必填字段见 [索引格式](maintain-index.md#索引格式)。字段缺失或类型不符会报 `metadata` 问题。
- `title`、`summary`、`dst_build` 为非空字符串；`aliases`、`sources`、`tags` 为字符串列表，元素非空。`tags` 仅取自下方标签分类法。
- `sources` 相对源码 `scripts/` 根，使用 `/` 分隔；不得以 `/` 开头、含 `:`、`\`，或包含空、`.`、`..` 路径段。传入 `--source-root` 时，每项须指向该根内实际存在的文件。
- `created`、`updated` 为 `YYYY-MM-DD` 有效日期，且 `created` 不晚于 `updated`。
- `reliability` 仅接受 `verified`；`validation` 仅接受 `source-reviewed`、`runtime-tested`；`status` 仅接受 `active`、`review-needed`、`archived`。

源码知识页可选 `size_class: simple | standard | complex`，省略按 `standard`；仅选择非默认档时需要填写。索引和 cookbook 不使用此字段，选档见下方“文件大小”。这不改变上述 12 个必填字段，已有页不要求补填。

## 命名与归属

- 文件名小写加连字符，代码、路径和标识符保持原文，正文中文；技术术语保留必要英文并解释实际职责，不按日常词义强行直译。Wiki 链接从 `wiki/` 起算并省略扩展名，例如 `[[reference/components/index]]`；案例引用可定位到具体章节，有实际关系时互链。
- 机制页归 `wiki/reference/` 的 components／prefabs／stategraphs／api／mechanisms，任务骨架归同级 cookbook。`mechanism` 承载行为、UI、世界生成内部流程和数据消费等主题，按实际职责建子主题；公开接入约定仍归 API。API 多页主题共用目录（如 `reference/api/modinfo/`），组件自身接口仍归组件页；未落地知识不建空分类。
- 通用任务骨架用 `type: cookbook`，归 `wiki/cookbook/`，如 `new-item.md`、`new-recipe.md`。

## 章节写法

### 页面结构

- **模板同步：** 三份模板是本节结构的实例；改动章节集合须同步三份模板。
- **标题层级：** reference 知识页的“快速判断／验证记录”、cookbook 的“适用条件／边界与验证”保留为二级标题，供查询工具识别并随选定章节返回。其余按需内容可用具体需求命名，职责须符合下文；能归入主节的用三级小节，独立流程或协作需要整体说明时才单开二级章节，避免重复展开。
- **定义与机制页：** component／stategraph／api／mechanism 共用“快速判断／关键接口／典型接入／常见陷阱与限制／验证记录”；无内容省略，状态／行为／数据消费链需要时补“关键流程”。Prefab 使用下表中模板的专用结构。
- **cookbook：** 采用“适用条件／最小 demo／按需求扩展／边界与验证”四节：demo 明示文件、加载、完整必要代码、资源和替换点；扩展给需求到实际机制章节的少量链接；末节记组装限制、源码依据、版本及实际验证范围。沿用现有元数据，不强套组件表格或另建模板；无核验依据不发布可用 demo。

仅新建或重组 reference 知识页时，按类型选择下表中的一份模板，成页删除占位和说明。非组件或归属不明时才追加[类型选择](source-types.md)，只读选型与命中差异；Prefab 关系核验读其中的 Prefab 指引。

| 页面类型 | 模板 |
|---|---|
| component | [组件模板](../../assets/templates/component.md) |
| prefab | [Prefab 模板](../../assets/templates/prefab.md) |
| stategraph／api／mechanism | [机制模板](../../assets/templates/mechanism.md) |

### 章节内容

- **快速判断：** 说明职责、对象与适用条件；“优先使用／重要副作用／修改边界”各一短条目，附证据入口。摘要、别名与场景标题保留需求措辞和必要生效范围，不靠 tags 推断。
- **关键接口：** 只选所需接口／字段／配置项，给参数、返回或约束、消费者、条件、副作用及证据，复杂内容可分小节，状态／行为顺序用短流程。默认赋值与已核验类型分开，注释不算初始化。未知保留，不从单个调用或编辑器公共模型补造接口。新增或修订关键数值后回读定义与实际结算，核对适用条件、单位及公式符号，区分配置、推导与实测。
- **典型接入：** 机制方案、案例与教程放典型接入，前提、位置、理由、单位、生效／撤销与验证按知识维护执行。独立读取案例所需的来源、宿主与清理条件放在“快速判断”或父节引言，案例小节只写自身差异。简单源码路径附接口／案例；复杂机制才增源码入口短索引，链接正文，不复制代码。
- **Lua 片段：** `lua` 围栏内使用语法完整的片段；不能独立解析的布局数据或带省略的节选，使用 `text` 围栏并注明为展示节选，或在不改变含义的前提下包装为 `local data = {...}` 等可解析片段。供直接使用的示例仍须满足完整示例要求，不得换围栏规避语法检查。`modmain` 示例须核验名称是否由模组环境提供；未提供的游戏全局通过 `GLOBAL` 获取，并注意世界对象的可用时机。
- **对比与协作：** 按需补对比或协作，给条件、推荐／分工与双方依据。
- **生命周期：** 生命周期信息优先归入关键接口或案例，触发顺序、状态恢复或清理协作需要整体说明时才单开“生命周期”；核验实现与宿主触发，事件区分接收／监听对象，语法引用不算硬依赖。
- **原版参照：** 归入典型接入，只选能帮助选型的不同模式，复用已有证据，核验注册名／工厂链，不维护 Top 20 或完整反向清单。
- **陷阱与待核验问题：** 陷阱记触发、表现、原因、解决方式／边界与证据，复杂问题用同节小节；有缺口再增待核验问题。错误命题标“误区”，正确事实或限制用正向表述（可标“边界”），避免脱离上下文后真假难辨。
- **验证记录：** 关联已核验结论／案例及缺口，可复用已有依据。行数、字节、锚点数留在校验输出或交付回报。
- **相关链接：** 必要相关链接置页尾。
- **LuaCATS：** 只链接固定版本的实际类型来源及核验范围，不设必填节或复制声明；候选不充当确定类型，实际类型维护才读接口核验。

### 复用与问题反馈

- **跨页复用与拆分：** 跨页机制在主要具体页维护，其他页链接章节；cookbook 只保存通用任务骨架。大页先按章节定位，确需拆分按具体对象／接口主题分工，不另建任意组合方案或陷阱页。
- **模板缺口：** 生成／重组中，若已核验内容无法由现有章节职责与允许的表达方式清楚承载，且本次或已有记录中存在多个同类实例，在完成报告中列为“模板缺口”，附相关页面／拟建页、具体内容及现有结构不适用的原因；不为寻找重复实例扫描全库。继续完成不受影响的内容，由独立工程维护任务决定是否调整模板。不得据此自行新增页面类型、目录分类或必填章节，也不直接修改本 Skill 包。
- **规则错误：** 可复现的规则冲突、错误命令或失效链接，发现一次即可在完成报告中说明位置、复现条件与影响，不等待同类实例；同样不自动转为本 Skill 包的修改任务。

## 文件大小

Wiki Markdown 须同时满足物理行数与 UTF-8 字节预算，计入 frontmatter、代码和空行，1 KiB = 1024 字节。批量同族页按注册数和证据量粗估。预计还需复审的页可酌留 1–2 KiB 和少量物理行数。预算内的有效内容可直接保留。

| 文件类别 | 最多行数 | 最大字节 |
|---|---:|---:|
| 根导航 `wiki/index.md`（含 Top 30） | 80 | 8 KiB |
| 分类／主题／叶级索引 | 240 | 24 KiB |
| component／prefab／stategraph／api／mechanism 知识页（默认标准档） | 240 | 32 KiB |
| cookbook 骨架页 | 360 | 32 KiB |

### 源码知识页分档

仅 component／prefab／stategraph／api／mechanism 使用下表。新建或实质增修时按本页覆盖的接口、条件、流程与协作选档；源码行数仅作初筛，不按文件总长、sources 累计行数或重复数据量等比例扩额。简单页优先选 `simple`，通常内容使用 `standard`；旧页默认保持标准档，不为本规则批量重写。

工具按本节固定标题与下表列序读取分档；基础三列表与此四列表分开维护，`standard` 须与基础表的默认知识页预算一致。

| size_class | 适用情况 | 最多行数 | 最大字节 |
|---|---|---:|---:|
| `simple` | 单一职责、少量接口与条件 | 120 | 16 KiB |
| `standard` | 多接口、必要接入与常见限制 | 240 | 32 KiB |
| `complex` | 需整体说明的多状态、多变体、复杂生命周期或协作 | 480 | 64 KiB |

选择 `complex` 时，在已有“快速判断”或“验证记录”内简记需要整体保留的范围。按机制复杂度选档，多个可独立使用的主题按各自职责组织。

压缩时优先去重、收短示例说明，保留影响结论的门禁、时序、例外、否定断言的覆盖范围及证据。仍超出任一上限时，符合复杂度才调整档位，否则按对象／接口主题或有实际差异的任务拆分；主地址保留短摘要和所需支撑页入口，并更新索引与互链。完整案例的条件、代码、清理和证据保持关联，不能为达标删必要上下文或机械截断。不可拆的 demo 可随页提供必要示例文件，正文保留文件清单、取得／加载方式、限制及验证；文件组织在实际交付时确定，不提前建空目录。复杂页仍按章节查询，不因写作预算变大而提高默认查询输出预算。

生成器／校验器须报告实际行数、字节、适用档位／上限和超限位置，超限停止发布该页并给精简／拆分建议，禁止静默截断。可选工具箱的 `scripts/tools/verify/validate_page.py` 通过 `--format` 指向本文件，读取本节阈值和下述标签；缺工具／环境时仍可人工量取。已有案例增修只需按需读取本节，不加载整份模板或接口契约。docs、Skill 规则／模板、维护日志、Lua 示例、源码及机器数据不套用知识页上限；源码／候选输出预算按各工具约定。

## 标签

- 组件：component, lifecycle, callback, state-machine
- Prefab：prefab, creature, building, item, food, equipment, fx
- 任务骨架：cookbook（配合实际内容标签）
- API：engine, global, event, network, modding
- 机制：mechanism, ai, ui, worldgen, data
- 常量：tuning, actions, equipslots
- 功能主题：recipe, aura, energy, loot
- 问题主题：network-sync, post-init, server-client（用于包含相关限制的知识页）
- Meta：overview, glossary, changelog, decision

Prefab 页保留 `prefab`，在“快速判断”说明主要对象类别；按已核验的构造、交互与使用链选择下列标签：

| 标签 | 对象职责与选择依据 | 易混边界 |
|---|---|---|
| `item` | 可拾取、由库存持有的物品，核对 inventoryitem 等实际接入 | 建筑装有物品不等于建筑自身是物品 |
| `equipment` | 可装备并参与穿脱／装备槽行为，核对实际装备链；通常与 item 并用 | 持握外观、跟随持有者的 FX 不自动算装备 |
| `food` | 可被进食的食物，核对 edible 与实际食用条件；物品形态通常同时用 item | 有新鲜度、食物外观或烹饪用途不单独证明可食用 |
| `building` | 建造／部署后作为世界设施使用，核对设施构造与交互 | 固定在地面不单独证明是建筑；placer 只是放置预览 |
| `creature` | 角色或生物实体，核对其生命、行为或交互职责 | 单有 health、动画或 Brain 不是充分分类依据 |
| `fx` | 承载视觉／声效表现，如粒子、动画、跟随效果或拖尾，核对实际效果链 | 可同时具有温度、伤害、光环等玩法作用，正文须写明 |

- 标签可组合，但每项都描述本对象已核验的职责；不会因引用某组件、掉落物品、附带特效或由法杖召唤而继承关联对象的类别。
- 同页多形态／变体在“注册与构造”标清各自类别；页面 tags 概括主要对象，不把附带的 placer／FX 类别无差别赋给整个主体页。其他世界实体或类别未定者用正文说明，不强套上表，也不为单个对象临时增加标签。
- Wiki 标签与游戏实体 tags 分开；名称后缀、源码目录、单个组件或游戏标签仅作线索。类别仍未知时注明缺口，不凭 `fx` 后缀认定纯视觉；功能／限制由正文及证据表达，不能只靠分类标签。

复用已有标签，新增分类先改本节。aliases 匹配需求措辞，tags 分类，不互相替代；注册名按主要归属写入 aliases（一个注册名只保留一个主要页）；额外检索别名按需补充，描述性别名允许重叠，不要求全部别名唯一，共享描述性别名不构成归属冲突。FX 页不要求官方 `NAMES`／po 名，标题和别名可用注册名＋效果描述。
