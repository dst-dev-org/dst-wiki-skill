# DST Wiki 模组经验提炼

仅用户要求从指定模组／功能提炼共享经验时读取；直接增补已知骨架走 [骨架维护](maintain-skeleton.md)。K 尚未确认时才按 [路径约定](../setup/paths.md) 定位，已确认则复用。现成模组和本次已完成开发均可作为输入，开发完成不自动写共享库。

## 定向分析与去除专属依赖

1. 按用户给定的模组、功能或文件范围，定向确认项目约定、modmain 注册／加载、相关实现、必要配置／资源和本地 Wiki。只给目录时先列入口与相关文件／标识符，不读整个项目；信息足够就继续，无法确定要提炼的功能时再集中确认。
2. 有明确 Git 基线时用改动文件／函数缩小范围，再读当前完整实现及依赖；未提交变更同样核对。Git diff 是定位线索，不能替代加载、初始化或清理上下文；不为这项任务提交／切分支或修改模组。
3. 追踪 demo 实际调用的自定义组件／全局函数、加载代理、配置、动画／图标和共享辅助文件。区分原版能力、可去除的专属包装和必须保留的依赖；去除后仍给完整必要文件与加载方式，无法去耦则留在模组 Wiki，不包装成通用骨架。共享 demo 用明确可取得或替换的资源，不复制模组专属资源／整套框架。已有本地 Wiki 作线索，结论核对当前代码。
4. 组装经验归 cookbook，确有增补时进入前述骨架维护；接口行为和机制陷阱归主要 reference 页，按需切换 [知识维护](maintain-wiki.md) 并以链接复用。模组专属骨架、约定和差异留该模组，提炼请求不自动授权双写或初始化其 Wiki。

## 对照已有知识与交付

1. 将功能归纳为少量“对象／效果／触发条件／组装方式”，定向搜索相关 cookbook／reference；每轮初始候选最多 5 个。先读摘要、适用条件和所需章节，比较新增模式、必要上下文或已核验冲突；要修改时再读页面全文。游戏接口结论缺证据时按 [查询证据](../query/query.md#证据) 定向核验关键实现与必要消费者，模组写法不证明通用机制正确。
2. 已有覆盖且无实际变化时报告命中页和依据，不改正文、日期或日志。无法去耦或证据不足时列明依赖／待核验缺口，不发布可用共享 demo，也不自动写模组自己的 Wiki；一次开发或 bug 不自动成为“常见方案”。
3. 只有实际需要写入时才读取对应维护文档，复用本次已确认的定位、匹配和有效证据，不重复分析模组或展开全部规则。报告可复用部分、知识归属、实际改动与仍待核验范围；来源、版本和运行边界按写入流程记录，无 Git 时不造 commit。
